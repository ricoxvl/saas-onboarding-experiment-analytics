# SaaS Onboarding & Experiment Analytics

An end-to-end product analytics case study exploring how a redesigned SaaS onboarding experience affects activation and day-28 retention.

**Status:** Phase 3 — filterable Streamlit dashboard with four working views, cohort filtering, experiment inference, guardrail review and planning sensitivity.

> **Data integrity:** All data generated by this repository are **synthetic**, for learning and demonstration. Simulated results are not customer outcomes or evidence of a deployed product experiment.

## Business question

Does a guided onboarding flow (treatment), compared with the standard flow (control), increase **day-28 retention** among new SaaS signups without harming activation or onboarding completion?

We model a self-serve B2B SaaS product where new users sign up, create a workspace, connect an integration, and optionally invite a teammate. Activation is defined *before analysis* as completing both workspace creation and integration connection within seven days.

## Stack

- **Python 3.10+** (standard library) for deterministic data simulation and statistical analysis
- **SQLite / SQL** for event and cohort analytics
- **Unittest** for automated statistical and event-level quality checks
- **Streamlit / Plotly / Pandas** for a polished, interactive portfolio dashboard

## Run locally

1. Clone this repository and enter its folder.
2. Install the package:

   ~~~bash
   python -m pip install -r requirements.txt
   ~~~

3. Generate a reproducible synthetic dataset:

   ~~~bash
   python -m saas_analytics.simulate --users 4000 --seed 42
   ~~~

4. Calculate funnel metrics, cohorts, A/B effects, guardrails, segments, power sensitivity, and a pre-analysis quality audit:

   ~~~bash
   python -m saas_analytics.analyze
   ~~~

5. Launch the interactive dashboard:

   ~~~bash
   streamlit run dashboard/app.py
   ~~~

   The browser opens at **http://localhost:8501**. The dashboard automatically generates a seeded, validated synthetic demo dataset on first launch, including Streamlit Cloud. You do not need to check generated data into Git.

6. Run automated tests:

   ~~~bash
   python -m unittest discover -s tests -v
   ~~~

## Dashboard views

| View | Interactive capabilities |
| --- | --- |
| **Overview** | Signup, activation, D28 retention, onboarding errors, retention chart and user-type breakdown |
| **Onboarding funnel** | Control vs treatment onboarding conversion, step counts and friction metrics |
| **Retention & cohorts** | Monthly cohort trends, D7/D28 toggle, exploratory segment effects and BH-adjusted q-values |
| **Experiment lab** | Live recomputation of effect sizes, confidence intervals, p-values, 50/50 allocation diagnostics, guardrail tolerance sensitivity and sample-size/MDE planning |

**Sidebar controls:** change synthetic seed or user count, filter by pre-treatment user segment and signup cohort(s), or export the selected simulated user records as CSV. All visible comparisons recalculate for the selected population. The guardrail slider is explicitly exploratory; changing it is not a valid pre-registered decision rule. The dashboard uses no external APIs and no real customer information.

## Generated outputs

- `data/generated/users.csv` — user-level experiment assignment, onboarding, activation, retention
- `data/generated/events.csv` — timestamped user events
- `data/generated/saas.db` — queryable SQLite database
- `reports/generated/experiment_results.json` — sample sizes, effect size, confidence interval, p-value, SRM check
- `reports/generated/funnel.csv` — onboarding conversion by experiment group
- `reports/generated/cohorts.csv` — signup-month activation and retention
- `reports/generated/summary.md` — readable decision summary
- `reports/generated/quality_checks.json` — event integrity and experiment readiness checks; analysis fails on invalid data
- `reports/generated/segments.csv` — exploratory team/solo and signup-month retention differences, BH-adjusted q-values
- Planning MDE, sample-size requirements, balance diagnostics and onboarding/support guardrails are embedded in `experiment_results.json`

Generated data and reports are ignored by Git. Rerun the pipeline to regenerate them.

## Methodology at a glance

- **Assignment:** 50/50 seeded user-level randomization; analyze by assigned group (intention-to-treat).
- **Primary outcome:** binary return activity on day 28 (the data generator records a day-28 return event).
- **Supporting metrics:** D7 activation; onboarding funnel completion; cohort retention.
- **Negative-outcome guardrails:** D7 onboarding errors and D7 support tickets (simulated events, smaller is better).
- **Exploratory analysis:** team/solo and signup-month contrasts with Benjamini-Hochberg FDR-adjusted q-values (one family of retention subgroup comparisons).
- **Planning:** approximately required sample sizes for +2, +3, and +5 percentage-point retention lifts, plus 80%-power minimum detectable effect (MDE) using a reference baseline. This is **not observed power**.
- **Statistics:** difference in proportions (treatment minus control), two-sided pooled z-test, unpooled 95% CI, chi-square sample-ratio mismatch (SRM) check.
- **Important limitations:** all outcomes are simulated; no production users, no evidence for a real causal impact, normal-approximation inference, and no confirmatory multiplicity adjustments for the secondary guardrails. An illustrative +2 pp negative-outcome guardrail tolerance is a design exercise, not a pre-registered launch criterion.
